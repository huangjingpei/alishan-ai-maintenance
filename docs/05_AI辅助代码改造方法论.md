# AI 辅助大规模代码改造方法论

从"抖多客恢复仓标识符可读化"实战提炼的可复用方法论。适用于任何 AI（vibe coding）执行的大规模机械/半机械代码改造：重命名、重构、框架迁移、API 替换、死代码清理。核心只有一句话：

> **AI 的每一次输出都必须经过一道它自己无法影响的独立验证门，门不过就停，绝不绕行。**

## 0. 信任链总览

```
AI 改造工具（不被信任的执行者）
   ↓ 每文件
门 1：静态语法解析自检（改完至少还是合法代码）
门 2：AST 语义等价校验（改造前后语义一致）
门 3：仓库既有校验（validate / lint / 单测）
门 4：运行时黄金基线（行为快照逐字节一致）
门 5：端到端冒烟（真实启动/真实执行路径）
   ↓ 全过
每文件独立 git 提交（原子回滚单元）
```

任何一门失败：立即停止批量流程 → 进入 §5 失败处置协议。

## 1. 地基勘察（写第一行改造代码之前）

改造前必须回答三个问题，全部要有**证据**而非猜测：

1. **我改的东西真的在运行吗？** 本项目实证：入口 `main.js` 加载 `.jsc` 字节码，字节码再 require 可读的 `./main/*`、`./shared/*`——所以可读文件就是运行时真身，改名会真实生效。如果改的是死代码，整个验证体系都是空转。
2. **改了会被什么机制拦截吗？** 对 `protection-manifest.json` 做了三层探测：可读运行时代码 grep（零引用）→ `.jsc` 字符串提取（只有生命周期事件名，无哈希/清单字符串）→ 结论"无运行时强制校验"，并用真实启动做最终背书。
3. **环境有什么硬事实？** 例：`better-sqlite3` 按 Electron ABI 编译 → 黄金基线必须用 `ELECTRON_RUN_AS_NODE=1 electron.exe` 跑，用 node 跑会得到误导性的 ABI 错误。环境事实决定验证工具的形态。

## 2. 风险面扫描（决定工具要多"聪明"）

对改造对象做全量扫描，列出会让"简单替换"出错的构造。本项目扫描结论：无 `eval`/`with`、无 hex 标签、无字符串动态访问、无 hex 对象键，仅少量 `obj._0x` 成员属性（不触碰）——所以纯 AST 绑定级改名是安全的。如果扫出 `eval`，就必须先收敛它，否则任何静态工具都有盲区。

**产出物是一份"危险构造清单"，工具的设计直接由它决定。**

## 3. 验证器与改造器同步构建（顺序很重要）

原则：**改造器永远不允许在验证器就绪前对真实语料运行。**

- **AST 语义等价校验器**（本仓 `scripts/verify-ast-equiv.mjs`）：把两棵 AST 的绑定标识符规范化为 b1/b2/... 后整体序列化对比。重命名引入的遮蔽、漏改、引用错位全部会破坏序列一致性。要点：
  - 对象键、成员属性、标签等非引用位按**结构**识别跳过，不能靠作用域查找（改名后键名可能撞上绑定名）；
  - 声明节点按 `binding.identifier` 节点**身份**解析，不能走 `getBinding`（嵌套同名遮蔽会假阳性，见 §5）。
- **运行时黄金基线**（`scripts/golden-db-harness.mjs`）：对模块打固定输入序列，序列化全部输出与副作用，时间戳/临时路径掩码后 diff。AST 等价证明"代码没变"，黄金基线证明"行为没变"——两者互补，因为等价校验器本身也是代码，也可能有 bug。

## 4. 先合成用例，再真实语料

在真实文件上运行前，用**手工构造的合成文件**覆盖所有危险模式跑一遍改造器+校验器：解构别名、同名遮蔽跨作用域、与祖先绑定撞名、与全局未绑定引用撞名、成员属性/对象键不触碰。本项目的冒烟测试实际抓出了改造器 2 个真 bug（撞名检查种子缺失、全局引用捕获）——**在 8000 行真实文件上抓这两个 bug 的成本是完全不同的量级**。

## 5. 门禁失败处置协议（方法论的心脏）

门禁报警只有两种可能，处置路径完全不同，**不允许第三种（"看起来没问题，继续吧"）**：

```
门禁失败
├─ 改造器真 bug（语义被改变）
│    → 定位 → 修复 → 该文件还原重跑 → 全部门禁重走
│    → 实例：`path: _0x1` 被改成 path 捕获顶层模块 → 补碰撞检查种子
└─ 校验器假阳性（代码等价但校验器误判）
     → 写对齐诊断工具定位分歧（按结构对齐逐标识符对比绑定解析）
     → 判定依据：受影响的只是声明节点解析还是真实引用配对
     → 修复校验器 → 关键动作：**全量回验所有已通过文件**（校验器变了，旧结论作废）
     → 实例：function fn 内嵌 function fn，声明 id 的 getBinding 命中嵌套绑定
```

判别口诀：**运行时引用的配对变了 = 真 bug；只有声明节点自身的解析变了 = 假阳性**。拿不准就回到源码人工比对分歧点上下游（本项目正是靠打印旧源码 50-100 行确认 78/87/90 行的调用目标才定案）。

## 6. fail-fast 流水线批量推进

试点文件（小→大，全门禁走通、跑通运行时冒烟）之后才批量。流水线规则：

1. **每文件原子化**：改名 → 等价校验 → 任何一步失败立即终止整个批次；
2. **批内先暂存，门禁全过再逐文件提交**：批次里 validate/test 失败时，一个提交都不落盘（本仓 `.temp/clean-chunk.sh`）；
3. **每文件独立提交**，message 记录改了多少处——出问题 `git revert` 单文件即可；
4. **固定节奏插入全量门禁**：每批 validate + 既有测试；每若干批一次启动冒烟；数据库类文件每批跑黄金基线 diff。

## 7. 分层命名策略（信息来源决定手段）

机械推导永远优先于 AI 猜测，AI 只处理无结构线索的残余：

| 层 | 信息来源 | 手段 | 风险 |
|---|---|---|---|
| 1 | 结构线索（解构别名 `key: _0x1`、require 模块名、参数默认值） | 规则推导 | 零 |
| 2 | 导出映射（`return { apiName: fn37 }`） | 键名回填 | 零 |
| 3 | 无结构线索的函数/变量 | **AI 读函数体起名**，映射表落盘可审查 | 名字可能不精确，但走同一套碰撞检查+全部门禁；不确定时宁可保守 |

关键认知：第 3 层 AI 命名的**错误代价是"名不达意"，不是"语义破坏"**——因为名字只通过作用域安全检查生效，语义等价由门 2/4 兜底。这就是 AI 可以安全参与大规模改造的边界条件。

## 8. 工程习惯清单

- git 是唯一真相源；改造前版本永远可从 `git show HEAD:path` 取回，参照文件随取随生成；
- 端口/进程类冒烟失败（如 EADDRINUSE）先清环境残留再重试，不要误判为改造引入的回归；
- 预期内的环境报错（如 Vite 开发服务器不存在的回退）要记录在案，避免每次都当新问题排查；
- 工具脚本本身入库、文档化（`docs/04`），让下一次改造从"复用工具"而不是"重新发明"开始；
- 进度可度量：`grep -oE "_0x..." | wc -l` 这类单一数字指标，让"还剩多少、这批做了多少"始终可见。

## 9. 迁移到其他项目的检查清单

1. §1 三问的证据是什么？
2. 危险构造清单扫了吗？最危险的构造是什么，工具如何规避？
3. 语义等价怎么证明？没有 AST 等价就至少要有行为快照；
4. 验证器自己怎么被验证过（合成用例）？
5. 门禁失败时的二分路径写下来了吗？
6. 最小回滚单元是什么？一次提交改了多少东西？
7. AI 参与的边界在哪层（§7）？AI 的输出经过哪几道它影响不了的门？
