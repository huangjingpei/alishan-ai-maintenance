# 抖多客恢复版：编译、重封装与发布指南

文档版本：1.0  
适用程序版本：2.9.89  
基线平台：Windows x64、Electron 24.8.8、Chromium 112.0.5615.204  
编写日期：2026-08-27

## 1. 文档目的

本文说明如何在没有原始 TypeScript、Vite 和 Electron 工程的情况下，对已经恢复的发行版代码进行修改、静态校验、重新封装 `app.asar`、生成便携测试目录，并进一步制作 Windows NSIS 安装包。

这里的“编译”需要分成两种含义：

1. **短期发行版修补**：修改恢复出来的 JavaScript、CSS、HTML 或 JSON，再重新封装 ASAR。这条路线现在可用，也是本文的主要流程。
2. **长期源码重建**：重新建立真正的 Electron/Vite 源码工程，再从源文件执行 `npm run build`。当前发行包缺少原始源码、构建配置、注释和一方 sourcemap，暂时不能完整还原原来的编译流程。

不要把“ASAR 重封装成功”误认为“程序运行验收成功”。最终发布必须经过隔离环境运行测试、升级测试和代码签名。

## 4. 发布前必须确认的公司参数

以下项目不能从当前安装包中可靠地全部恢复，正式发布前必须由公司确认：

### 4.1 正式 appId 和升级标识

测试配置暂时使用：

```yaml
appId: com.alishan.aihuoke.recovered
```

这是占位值，不能直接用于正式发布。应从以下位置查找旧值：

- 原来的 `electron-builder.yml` 或 `package.json`；
- 已安装机器的 Windows 卸载注册表；
- 旧 CI/CD 配置；
- 安装、升级服务或运维文档。

如果新旧 `appId`、安装目录标识或升级 GUID 不一致，Windows 可能把新安装包视为另一款应用，导致无法覆盖升级、出现两个卸载项或用户数据目录变化。

### 4.2 代码签名证书

当前生成的测试安装包没有 Authenticode 签名。正式发布必须使用公司的 Windows 代码签名证书，并把证书和密码保存在 CI 密钥库中，禁止提交到 Git、Markdown、脚本或聊天记录。

### 4.3 正式图标和版权信息

测试安装包使用了 electron-builder 默认安装器图标。正式版需要公司提供 `.ico` 文件，并确认：

- 产品名称；
- 公司名称；
- 文件描述；
- 版权信息；
- 安装器和卸载器图标。

### 4.4 后端与产品配置

发行版清单中包含产品变体、API 地址和环境变量名称。修改以下内容前需要后端负责人确认：

```text
API_BASE
PRODUCT_SLUG
PRODUCT_TOKEN
API_BASE_2
API_BASE2_REGIONS
```

不要把新的密钥、令牌或签名私钥硬编码进前端发行包。

## 5. 推荐的短期修改流程

### 5.1 建立私有维护仓库

不要直接在 `.reverse_analysis` 中长期开发。建议创建一个公司私有仓库，至少包含：

```text
app/                 # 从 readable-source 导入的可读代码
baseline/            # 原始哈希和恢复报告，不频繁改动
packaging/           # electron-builder 配置
scripts/             # 校验、ASAR 封装和发布脚本
docs/                # 架构、接口、发布和交接文档
tests/               # 最小回归测试
```

原始安装包、完整 Electron runtime 和大体积发布产物建议放公司制品库，不建议直接提交普通 Git；确需版本管理时使用 Git LFS，并限制仓库权限。

### 5.2 创建修改分支

示例：

```powershell
git switch -c fix/message-center-filter
```

一次分支只解决一个明确问题。不要在同一次提交中同时批量重命名、格式化全部文件和修改业务逻辑，否则无法有效审查差异。

### 5.3 定位代码

优先使用 `rg` 搜索界面文字、IPC 名称、接口路径、日志文字或数据库表名：

```powershell
$AppRoot = 'E:\zhibodou-ai\zhibodou\.reverse_analysis\readable-source'
rg -n '消息中心|message-center|ipcRenderer|CREATE TABLE' $AppRoot
```

常见目录：

- `dist-protected/main`：Electron 主进程的外部业务模块；
- `dist-protected/shared`：自动化、页面解析和通用规则；
- `dist-protected/automation-preload.js`：页面注入和 IPC；
- `dist-protected/renderer/assets`：前端 ES Module bundle；
- `dist-protected/renderer/index.html`：前端入口；
- `dist-protected/main/dbManager.js` 和 `dbMigration.js`：SQLite 与迁移。

### 5.4 修改原则

1. 保持文件名和相对路径不变，特别是 renderer 的带哈希文件名。
2. 保持 CommonJS 与 ES Module 形式不变。
3. 不要随意修改 IPC channel 字符串；主进程、preload、renderer 三端必须一致。
4. 不要修改 `main*.jsc`。
5. 不要升级 Electron 或替换 `better-sqlite3.node`，除非计划重编全部原生依赖并重新验证 Bytenode 兼容性。
6. 修改数据库前先设计向前迁移和回滚方案，禁止直接删除生产用户表或字段。
7. 每次只修改必要文件，避免把无关格式化差异带入发布包。

## 6. 静态校验

当前恢复版的 267 个业务 JavaScript 文件已按 CommonJS/ES Module 类型通过语法校验。每次修改后至少执行：

```powershell
node --check 'E:\zhibodou-ai\zhibodou\.reverse_analysis\readable-source\dist-protected\main\dbManager.js'
```

renderer 文件是 ES Module，不能简单按 CommonJS 解析。建议在正式仓库加入统一的 Node 校验脚本，分别使用 `vm.Script` 和 `vm.SourceTextModule` 解析两类文件。

此外还应检查：

```powershell
$AppRoot = 'E:\zhibodou-ai\zhibodou\.reverse_analysis\readable-source'
rg -n '<<<<<<<|=======|>>>>>>>' $AppRoot
rg -n 'console\.log\(|debugger;' $AppRoot\dist-protected
```

第二条不是要求删除所有日志，而是确认没有把调试数据、令牌、Cookie 或用户隐私打印到正式日志。

## 7. 重新封装 app.asar

### 7.1 为什么必须解包 better-sqlite3

`better-sqlite3` 包含原生 `.node` 模块，不能普通地留在 ASAR 内。封装时必须使用 `--unpack-dir`，让它生成配套的 `app.asar.unpacked`。

### 7.2 已验证命令

```powershell
$SourceRoot = 'E:\zhibodou-ai\zhibodou\.reverse_analysis\readable-source'
$ResourceOut = 'E:\zhibodou-ai\zhibodou\.reverse_analysis\build-test\resources'

New-Item -ItemType Directory -Force -Path $ResourceOut | Out-Null

npx.cmd --yes @electron/asar pack `
  $SourceRoot `
  (Join-Path $ResourceOut 'app.asar') `
  --unpack-dir 'node_modules/better-sqlite3'

if ($LASTEXITCODE -ne 0) {
  throw 'ASAR pack failed'
}
```

本次验证结果：

- `app.asar`：17,521,637 字节；
- `app.asar.unpacked`：36 个文件；
- `better_sqlite3.node` 已位于 unpacked 目录；
- ASAR 内包含 `package.json`、`main.js`、`main.x64.jsc` 和业务目录。

检查内容：

```powershell
$AsarFile = 'E:\zhibodou-ai\zhibodou\.reverse_analysis\build-test\resources\app.asar'
npx.cmd --yes @electron/asar list $AsarFile | Select-Object -First 50
```

### 7.3 protection-manifest 风险

`dist-protected/protection-manifest.json` 保存了 293 个发行文件的 SHA-256。当前还不能确认 `main*.jsc` 是否会在启动时强制校验这些哈希。

因此：

- 不要把“反混淆后的全部文件”直接当成已通过运行验证的正式包；
- 首次运行测试时重点检查完整性校验错误；
- 未确认校验机制前，不要盲目删除清单或批量重写哈希；
- 如果确实存在公司自有完整性机制，应在重建源码工程时正式恢复其生成脚本和签名流程。

## 8. 生成便携测试目录

便携目录的做法是复制原始 Electron runtime，再替换 `resources/app.asar` 和 `resources/app.asar.unpacked`。

必须使用新的、明确的输出目录，禁止在原始 `payload` 上直接覆盖。

```powershell
$PayloadRoot = 'E:\zhibodou-ai\zhibodou\.reverse_analysis\payload'
$StagingRoot = 'E:\zhibodou-ai\zhibodou\.reverse_analysis\build-test\staging-2.9.89'
$ResourceOut = 'E:\zhibodou-ai\zhibodou\.reverse_analysis\build-test\resources'

if (Test-Path -LiteralPath $StagingRoot) {
  throw "输出目录已存在，请使用新的版本目录：$StagingRoot"
}

New-Item -ItemType Directory -Path $StagingRoot | Out-Null
Copy-Item -Path (Join-Path $PayloadRoot '*') -Destination $StagingRoot -Recurse -Force

Copy-Item `
  -LiteralPath (Join-Path $ResourceOut 'app.asar') `
  -Destination (Join-Path $StagingRoot 'resources\app.asar') `
  -Force

Copy-Item `
  -Path (Join-Path $ResourceOut 'app.asar.unpacked\*') `
  -Destination (Join-Path $StagingRoot 'resources\app.asar.unpacked') `
  -Recurse -Force
```

完成后应能看到：

```text
staging-2.9.89/
  抖多客.exe
  resources/
    app.asar
    app.asar.unpacked/
```

## 9. 隔离运行与冒烟测试

首次运行恢复版必须放在专用测试机或虚拟机中，不要直接覆盖员工的生产安装。

建议：

1. 禁止使用真实客户账号和真实客户数据；
2. 使用测试后端、测试账号和受控网络；
3. 先记录原版运行行为，再对比修改版；
4. 备份并隔离 Electron `userData`、SQLite 数据库和本地配置；
5. 监控崩溃日志、网络请求、数据库迁移和 IPC 错误；
6. 若程序出现完整性校验失败，停止发布并分析 `protection-manifest`，不要直接关闭安全检查。

最低冒烟测试：

- 程序启动和退出；
- 单实例行为；
- 登录、登出和令牌过期；
- 主界面所有一级页面打开；
- 数据库新建、读取和升级；
- 被修改的具体功能；
- 网络离线、超时和后端报错；
- 多显示器、缩放比例和窗口恢复；
- 重启后配置与任务状态；
- 不产生明文令牌、Cookie 或客户数据日志。

## 10. 使用 electron-builder 制作 NSIS 安装包

### 10.1 打包专用 package.json

在独立的 `packaging` 目录创建：

```json
{
  "name": "alishan-ai-packaging",
  "version": "2.9.90",
  "private": true,
  "author": "公司法定或正式发布主体",
  "description": "抖多客"
}
```

版本号必须与发布清单、后端兼容策略和发布记录一致。

### 10.2 electron-builder.yml

```yaml
appId: com.yourcompany.alishanaihuoke # 必须替换成公司的正式值
productName: 抖多客
electronVersion: 24.8.8
artifactName: ${productName}_${version}.${ext}

directories:
  output: release

compression: normal

win:
  target:
    - target: nsis
      arch:
        - x64
  executableName: 抖多客
  icon: build/icon.ico

nsis:
  oneClick: false
  perMachine: false
  allowToChangeInstallationDirectory: true
  createDesktopShortcut: true
  createStartMenuShortcut: true
  shortcutName: 抖多客
  uninstallDisplayName: 抖多客
  deleteAppDataOnUninstall: false
```

不要在没有产品、运维和数据负责人确认的情况下把 `deleteAppDataOnUninstall` 改为 `true`。

### 10.3 使用预打包目录生成安装包

```powershell
$StagingRoot = 'E:\zhibodou-ai\zhibodou\.reverse_analysis\build-test\staging-2.9.89'
$BuilderConfig = 'E:\zhibodou-ai\zhibodou\.reverse_analysis\build-test\builder\electron-builder.yml'

npx.cmd --yes electron-builder `
  --win nsis `
  --x64 `
  --prepackaged $StagingRoot `
  --config $BuilderConfig

if ($LASTEXITCODE -ne 0) {
  throw 'Installer build failed'
}
```

`--prepackaged` 很重要：它让 electron-builder 直接使用已经准备好的 Electron 目录制作 NSIS，而不是重新下载运行时、重新编译 Bytenode 或重建 `better-sqlite3`。

## 12. 代码签名与最终校验

代码签名应在 CI 或隔离发布机中完成。证书密码使用 CI Secret，不写入命令脚本。正式产物至少检查：


## 14. 常见故障

### `Cannot compute electron version`

在配置中明确指定：

```yaml
electronVersion: 24.8.8
```

### 找不到 `better_sqlite3.node`

检查是否使用了：

```text
--unpack-dir node_modules/better-sqlite3
```

并确认便携目录同时存在 `app.asar` 和 `app.asar.unpacked`。

### 安装成功但无法覆盖旧版本

优先核对正式 `appId`、安装器 GUID、产品名、安装范围和旧版本注册表信息。不要通过删除用户安装目录来“解决”。

### 启动时出现 bytecode 错误

Electron、V8 和 Bytenode 字节码必须匹配。确认仍使用 Electron 24.8.8，并且 `main.x64.jsc` 未被修改。

### 启动时出现完整性错误

检查 `protection-manifest.json` 与被修改文件的关系。保留日志和错误栈，先确认原有校验设计，再决定如何重建合法的清单生成流程。
