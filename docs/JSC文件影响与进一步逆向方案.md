# JSC 文件影响与进一步逆向方案

## 1. 直接结论

以下三个文件对项目有重要影响，必须保留：

```text
dist-protected/main.x64.jsc
dist-protected/main.arm64.jsc
dist-protected/main.jsc
```

它们不是缓存文件，而是通过 Bytenode 生成的 V8 字节码。`dist-protected/main.js` 的加载逻辑是：

1. 根据 `process.arch` 寻找 `main.<架构>.jsc`；
2. 如果架构文件不存在，再使用 `main.jsc`；
3. 如果都不存在，程序直接退出。

因此：

- Windows x64 主要加载 `main.x64.jsc`；
- ARM64 环境主要加载 `main.arm64.jsc`；
- `main.jsc` 是 fallback；
- 当前 `main.jsc` 与 `main.arm64.jsc` 的发行哈希相同，`main.x64.jsc` 是另一份字节码。

## 2. 它们可能负责什么

根据外部模块结构判断，JSC 主入口至少可能负责：

- Electron `app` 生命周期；
- 单实例锁；
- 主窗口和隐藏自动化窗口的创建；
- preload 路径设置；
- IPC handler 注册和模块装配；
- 数据库、设置和任务服务初始化；
- 登录状态和运行配置启动流程；
- 自动更新和协议处理初始化；
- `protection-manifest.json` 的完整性检查（目前尚未确认是否强制执行）；
- 全局异常、退出和清理逻辑。

外部的 `main/*.js` 与 `shared/*.js` 更像是被入口组合起来的业务模块。修改这些模块通常不要求直接修改 JSC，但前提是 JSC 仍会按原路径加载它们，并且没有拒绝被修改文件。

## 3. 日常开发是否可以暂时不处理

可以，但准确说法是：**保留并依赖它们运行，暂时不直接修改它们。**

以下需求通常可以先不逆向 JSC：

- 修改界面文字和样式；
- 修改列表筛选、数据格式化或导出；
- 修改 `main/*.js` 中已经外置的业务逻辑；
- 修改 `shared/*.js` 中的自动化规则；
- 修改已外置的数据库访问或迁移；
- 修改已有 IPC handler 调用的内部模块；
- 修复页面 DOM 解析和兼容问题。

以下需求很可能必须进一步处理 JSC 或重建入口：

- 新增顶层窗口或改变窗口创建顺序；
- 新增没有现有注册入口的 IPC 服务；
- 改变应用启动、单实例、退出或崩溃恢复；
- 改变全局认证初始化；
- 改变完整性校验；
- 改变主进程顶层模块装配；
- 升级 Electron；
- 移除 Bytenode 依赖。

## 4. 为什么不能直接“反编译回原源码”

JSC 保存的是特定 V8 版本使用的字节码，不包含完整的原始 JavaScript 文本。即使工具能够恢复部分控制流，也无法可靠恢复：

- 原始变量名；
- 注释；
- 原始文件拆分；
- TypeScript 类型；
- 原始格式；
- 构建前宏和环境注入；
- 与当前 V8 优化有关的全部语义细节。

Bytenode 字节码还与 Electron/V8 版本高度绑定。使用不同 Electron 版本加载时可能出现 bytecode rejected、cached data rejected 或直接崩溃。

## 5. 可行的进一步逆向路线

### 路线 A：静态字节码与字符串盘点

目标：确认字节码版本、可见字符串、模块路径、IPC 名称和错误信息。

优点：不运行程序，风险最低。  
缺点：只能获得有限结构，不能完整恢复控制流。

适合回答：JSC 是否引用某个模块、某个 channel 或某个安全检查。

### 路线 B：精确 Electron 24.8.8 环境中的受控动态观察

目标：在隔离虚拟机中记录：

- `require()` 加载顺序；
- `ipcMain.handle/on` 注册的 channel；
- `BrowserWindow` 创建参数；
- preload 路径；
- 启动阶段堆栈；
- 模块导出和关键函数调用；
- 完整性检查错误。

可通过受控 require hook、Electron API 包装、调试日志和异常堆栈完成。此过程不应关闭认证或安全控制，也不能使用生产账号和客户数据。

优点：能快速得到真实模块装配图。  
缺点：需要运行程序，必须使用隔离环境；观察到的是行为，不是原始源码。

### 路线 C：从外部模块反推并重建 main 源码

当前已经恢复大量 `main/*.js` 模块。可以通过它们的导出、IPC channel、日志和运行顺序，逐步编写新的普通 JavaScript 主入口。

推荐步骤：

1. 生成所有外部模块的 `require`/`module.exports` 图；
2. 生成 IPC channel 清单；
3. 记录窗口和 preload 配置；
4. 记录启动与退出生命周期；
5. 编写最小新入口，仅启动主窗口；
6. 按模块逐步接回数据库、设置、任务、消息和更新；
7. 建立集成测试，对比旧 JSC 入口行为；
8. 最终把 `package.json.main` 切换到新的源码入口。

这是长期最有价值的路线，因为最终可以彻底移除对不可维护 JSC 的依赖。

### 路线 D：第三方 JSC 反编译/字节码工具

可以用于辅助检查字节码结构，但输出质量和版本兼容性不稳定。它们不应被当作能够一键恢复原项目的方案。任何输出都必须通过 Electron 24.8.8 下的行为测试验证。

## 6. 建议优先级

当前建议：

1. 保留三个 JSC，锁定 Electron 24.8.8；
2. 先让外部 267 个 JS 模块具备稳定的修改、校验和打包流程；
3. 在隔离环境确认修改后的文件是否触发 `protection-manifest`；
4. 根据实际需求动态观察 JSC 的模块装配，而不是无目标地全面反编译；
5. 建立新的可维护 `main` 入口，逐步替代 JSC。

## 7. 什么时候启动专项逆向

满足任一条件时，应创建独立任务：

- 修改需求明确落在 JSC 内；
- 修改外部模块后没有生效；
- 启动时报完整性或 bytecode 错误；
- 需要新增顶层 IPC 或窗口；
- 计划升级 Electron；
- 公司决定彻底恢复正式源码工程。

专项任务应明确目标，例如“恢复所有 IPC 注册表”或“重建窗口启动流程”，而不是笼统要求“反编译整个 JSC”。
