文档版本：1.0  
适用程序版本：2.9.89  
适用对象：新入职开发、测试、技术负责人和发布人员  
编写日期：2026-08-27

## 1. 维护目标

这不是一个完整恢复的原始源码工程，而是一套从公司现有安装包中恢复的 Electron 发行版代码。新员工的第一目标不是立即“大规模重构”，而是：

1. 能准确定位功能；
2. 能做小范围、可审查、可回滚的修改；
3. 能稳定地重新封装和测试；
4. 逐步补齐架构、测试和构建资料；
5. 最终摆脱对混淆 bundle 和 Bytenode 字节码的长期依赖。

所有代码、安装包、账号和数据均应按公司内部敏感资产管理。

## 2. 入职第一天必须理解的事实

### 2.1 技术栈

- 桌面框架：Electron 24.8.8；
- Chromium：112.0.5615.204；
- 主进程模块：CommonJS；
- renderer：打包后的 ES Module；
- 数据库：SQLite，通过 `better-sqlite3` 9.6.0；
- 本地配置：`electron-store`；
- 网络：Axios、WebSocket、代理链和 SOCKS 代理；
- 核心入口保护：Bytenode `.jsc`；
- Windows 安装包：electron-builder + NSIS。

### 2.2 代码恢复程度

- 1,940 个 ASAR 文件已恢复；
- 267 个业务 JavaScript 文件已反混淆并通过静态语法校验；
- 字符串、接口名、SQL、IPC 名称和大部分控制流可以阅读；
- 原始注释、原始变量名和一方 sourcemap不存在；
- `main.x64.jsc`、`main.arm64.jsc` 和 `main.jsc` 尚未恢复成源码。

### 2.3 当前不能承诺的事情

- 不能承诺反混淆代码等于原始源代码；
- 不能承诺所有文件在修改后仍能通过可能存在的完整性校验；
- 不能直接升级 Electron；
- 不能直接把 renderer bundle 当成原始 React/Vue 组件工程；
- 不能在没有测试的情况下修改数据库结构、认证协议或自动化规则。

## 3. 目录结构

当前可读代码目录：

```text
E:\zhibodou-ai\zhibodou\.reverse_analysis\readable-source
```

核心结构：

```text
readable-source/
├─ package.json
├─ assets/
├─ dist-protected/
│  ├─ main.js
│  ├─ main.x64.jsc
│  ├─ main.arm64.jsc
│  ├─ main.jsc
│  ├─ automation-preload.js
│  ├─ manual-view-preload.js
│  ├─ build-variant.manifest.json
│  ├─ protection-manifest.json
│  ├─ main/
│  ├─ shared/
│  └─ renderer/
└─ node_modules/
```

### 3.1 `main/`

运行在 Electron 主进程中，负责窗口、数据库、网络、任务、更新、消息和系统能力。这里可以使用 Node.js API和 Electron 主进程 API。

### 3.2 `shared/`

包含主进程、preload 或自动化页面逻辑共享的规则，例如页面解析、筛选、任务控制、用户键规范化和抖音 URL 处理。

### 3.3 `automation-preload.js`

运行在自动化页面的 preload 上下文中，连接网页 DOM、注入脚本和 Electron IPC。此文件影响范围大，修改必须重点审查安全边界。

### 3.4 `renderer/`

应用自身的前端页面。当前只有打包后的 HTML、CSS 和 ES Module chunk，没有原始组件源码。文件名通常带内容哈希，但目前修改时必须保持现有文件名，因为 `index.html` 和其他 chunk 会引用它们。

### 3.5 `main*.jsc`

Bytenode/V8 字节码。新员工禁止直接用十六进制编辑器修改，也不要用其他 Electron 版本重新生成。需要改变其中逻辑时必须由技术负责人批准源码重建方案。

## 7. 标准修改流程

### 步骤 1：建立问题单

问题单至少写明：

- 当前行为；
- 期望行为；
- 复现步骤；
- 影响客户或内部角色；
- 数据库、接口、自动化平台和权限影响；
- 验收标准；
- 回滚方案。

### 步骤 2：建立分支

```powershell
git switch -c fix/具体问题名称
```

### 步骤 3：搜索入口

从用户可见文字、日志、IPC channel、API 路径或数据库表名开始：

```powershell
$AppRoot = 'D:\work\alishan-ai-maintenance\app'
rg -n '用户看到的文字' $AppRoot\dist-protected
rg -n 'ipcMain|ipcRenderer|webContents\.send' $AppRoot\dist-protected
rg -n 'CREATE TABLE|ALTER TABLE|PRAGMA' $AppRoot\dist-protected\main
```

### 步骤 4：建立最小调用链

在修改前写出一条最小链路，例如：

```text
renderer 点击按钮
  → ipcRenderer.invoke('task:start')
  → preload 暴露 API
  → ipcMain.handle('task:start')
  → main/entityLeadgenRunner.js
  → shared/entityLeadgenController.js
  → 数据库写入
```

只有确认链路后才修改。不要看到同名函数就假设它一定被当前页面调用。

### 步骤 5：小范围编辑

反混淆后仍可能存在 `_0x...` 变量。只在当前需要理解的函数或模块内做语义重命名，并把“纯重命名”和“行为修改”拆成不同提交。

建议提交顺序：

1. 添加测试或复现脚本；
2. 仅做必要的语义重命名；
3. 实现功能修改；
4. 更新文档；
5. 更新版本和发布记录。

### 步骤 6：静态校验

- CommonJS 文件用 `node --check`；
- renderer ES Module 使用团队统一的模块解析脚本；
- 检查合并冲突标记；
- 检查新增日志是否泄露敏感数据；
- 检查所有 IPC、接口和表名是否同步修改。

### 步骤 7：重新封装和隔离测试

按照《恢复版编译与打包指南》生成新 ASAR 和 staging 目录。每次使用新的输出目录，保留上一版作为比较基线。

### 步骤 8：代码审查

至少一名了解 Electron 主进程安全边界的开发者审查；数据库、认证、更新、代理和自动化相关改动建议由模块负责人加审。

### 步骤 9：发布审批

测试、产品、研发和发布负责人共同确认版本号、安装器身份、签名、哈希和回滚包。

## 8. 常见修改类型

### 8.1 修改界面文字或样式

1. 用 `rg` 搜索用户看到的完整中文；
2. 定位到 `renderer/assets/*.js` 或 `.css`；
3. 保持文件名不变；
4. 不要改变其他 chunk 的 import 路径；
5. 做 ES Module 语法校验；
6. 测试高 DPI、窗口缩放和不同分辨率。

长期应把页面逐步恢复为真正的组件源码，避免一直编辑 bundle。

### 8.2 修改 API 地址或产品变体

重点查看：

```text
dist-protected/build-variant.manifest.json
dist-protected/main/apiBaseRegion.js
dist-protected/main/runtimeConfig.js
dist-protected/main/authService.js
```

要求：

- 后端先确认新域名、TLS 证书和兼容版本；
- 地址优先通过受控环境配置注入；
- 密钥和产品令牌不得写进普通 JSON；
- 必须测试 401、403、429、5xx、超时和证书错误；
- 认证协议修改必须同时更新服务器端和客户端测试。

### 8.3 修改数据库

重点查看：

```text
main/dbManager.js
main/dbMigration.js
main/schemaMigrationUtils.js
各类 *Store.js、*Access.js、*Tasks.js
```

规则：

1. 所有 schema 修改通过版本化迁移完成；
2. 迁移必须幂等；
3. 使用事务；
4. 先备份，再迁移；
5. 同时测试空数据库、当前版本数据库和至少一个历史版本数据库；
6. 不允许依赖“卸载重装”解决迁移失败；
7. 大表迁移要评估锁表时间和磁盘空间；
8. 记录迁移开始、成功和失败，但不记录客户敏感内容。

### 8.4 修改 IPC

Electron IPC 是安全边界。新增或修改 IPC 时必须：

- 明确 channel 名称；
- 验证参数类型、长度和允许值；
- 不接受 renderer 提供的任意文件路径或任意命令；
- 不把完整 Node.js、文件系统或 shell 能力暴露给网页；
- 检查发送方窗口和会话；
- 主进程、preload、renderer 同步修改；
- 对失败返回结构化错误，不把内部栈直接显示给用户。

### 8.5 修改抖音页面选择器或自动化逻辑

重点查看 `shared/douyin*.js`、各 controller、runner 和 `automation-preload.js`。

要求：

- 使用专用测试账号；
- 保留速率限制、停止按钮和任务取消逻辑；
- 测试页面结构变化、空结果、登录过期和隐私页面；
- 不绕过平台安全机制；
- 遵守公司合规要求和平台规则；
- 对 DOM 选择器准备候选和降级路径；
- 日志中不要保存完整 Cookie、私信内容或不必要的个人信息。

### 8.6 修改更新逻辑

重点查看：

```text
main/appUpdate.js
main/appIdentity.js
build-variant.manifest.json
```

更新系统必须验证版本、下载来源、哈希和签名。正式 `appId`、安装器身份、更新元数据和签名证书必须保持一致。

## 9. 测试策略

### 9.1 测试分层

1. **静态层**：语法、文件清单、依赖和敏感信息扫描；
2. **模块层**：纯函数、筛选规则、解析规则、迁移辅助函数；
3. **IPC 层**：参数验证、超时和错误结构；
4. **集成层**：数据库、后端测试环境、窗口和任务生命周期；
5. **安装层**：全新安装、覆盖升级、卸载和回滚；
6. **业务层**：由产品和测试按真实流程验收。

### 9.2 每次改动的最低回归

- 启动与退出；
- 登录与登录过期；
- 主页面切换；
- 数据库读写；
- 被修改功能的正常、空数据、错误和取消路径；
- 离线与超时；
- 重启恢复；
- 安装和覆盖升级；
- 无敏感日志；
- CPU、内存和磁盘占用没有明显异常。

### 9.3 测试数据

测试数据必须匿名化或人工生成。不得复制真实客户数据库到个人开发机。需要生产问题复现时，由数据负责人生成最小脱敏样本。

## 11. 版本与发布规范

建议使用语义化版本：

- Patch：修复问题，不改变数据或接口契约；
- Minor：向后兼容的新功能；
- Major：不兼容变更，需正式迁移计划。

版本至少同步到：

- 维护仓库 `package.json`；
- packaging `package.json`；
- `build-variant.manifest.json`；
- 安装包文件名；
- 更新服务元数据；
- 发布说明和测试报告。

每个发布记录包含：

- 版本号；
- Git commit；
- 安装包 SHA-256；
- Authenticode 签名证书信息；
- 兼容的后端版本；
- 数据库 schema 版本；
- 已知问题；
- 回滚包及其哈希。

## 12. 安全与合规要求

### 12.1 密钥和令牌

当前恢复代码中存在与认证、运行配置、哈希和本地数据保护有关的逻辑。应安排安全审计，区分：

- 公开标识；
- 可轮换的客户端配置；
- 不应出现在客户端的真正秘密；
- 为历史数据兼容暂时保留的旧常量。

真正的服务端秘密必须迁移到服务端或公司密钥管理系统。

### 12.2 代码签名

开发测试包可以不签名，但不得发给客户。正式安装包和可执行文件必须使用公司证书签名，并由发布流水线记录证书指纹和时间戳。

### 12.3 第三方依赖

- 固定版本和锁文件；
- 定期执行漏洞扫描；
- 升级 Electron 前建立专门兼容项目；
- 原生模块升级必须重新编译并回归；
- 不从不明镜像下载构建工具；
- CI 使用受控 npm registry 或代理。

### 12.4 用户数据

数据库、任务记录、消息和账号信息可能包含敏感数据。日志、备份、导出和崩溃报告必须遵守公司数据分类、最小化和保留期限要求。

## 14. 第二周到第四周计划

### 第二周

- 为一个纯函数或筛选模块补测试；
- 理解一个 IPC 链路；
- 学习数据库备份和迁移测试；
- 修复一个低风险缺陷。

### 第三周

- 负责一个完整但非认证、非更新的功能；
- 增加结构化日志；
- 完成异常和取消路径测试；
- 参与一次安装升级测试。

### 第四周

- 独立提交一个中等规模变更方案；
- 更新功能地图和接口文档；
- 与负责人评估一个模块的源码重建计划。

## 15. 长期源码重建路线

长期让员工直接维护混淆发行代码，成本和风险都会持续上升。建议分阶段重建。

### 阶段 0：冻结可复现基线

- 保存原安装包、ASAR、Electron runtime 和哈希；
- 固定 Node、ASAR 和 electron-builder 版本；
- 建立一键静态校验、打包和制品归档；
- 建立最小冒烟测试。

### 阶段 1：恢复公共模块

优先把 `shared` 中的纯函数迁移到新的 `src/shared`：

- URL 解析；
- 文本规范化；
- 筛选规则；
- 用户键和去重规则；
- 时间和状态判断。

为每个模块补单元测试，并逐步使用有语义的变量名。

### 阶段 2：重建 renderer

- 识别当前前端框架和路由；
- 建立新的 Vite 工程；
- 按页面逐个恢复组件；
- 保持现有 IPC 契约；
- 使用截图回归或端到端测试对比旧界面。

### 阶段 3：重建 preload 和 IPC 契约

- 定义类型化 IPC schema；
- 为每个 channel 做输入验证；
- 缩小 preload 暴露面；
- 替换大型单文件 preload；
- 增加权限和会话检查。

### 阶段 4：重建主进程入口

- 根据外部 `main/*.js` 模块和运行观察恢复窗口生命周期；
- 恢复单实例、菜单、托盘、更新、数据库和任务注册；
- 用普通可维护源码替代 `main*.jsc`；
- 保持用户数据、数据库和升级兼容。

### 阶段 5：正式工程化

- TypeScript；
- ESLint、Prettier 和测试；
- CI 构建；
- 依赖锁定和漏洞扫描；
- 安装、升级和回滚自动化测试；
- 代码签名和发布审批；
- 构建产物 SBOM。

## 16. 必须升级给技术负责人的情况

遇到以下事项，新员工应停止自行修改并升级：

- 需求必须修改 `main*.jsc`；
- 发现启动完整性校验或字节码不兼容；
- 需要升级 Electron、Bytenode 或原生模块；
- 修改认证、授权、产品令牌或服务端签名；
- 修改自动更新、安装器身份或正式 `appId`；
- 修改数据库且无法保证回滚；
- 涉及真实客户数据或账号；
- 需要执行任意系统命令或扩展文件访问权限；
- 发现疑似硬编码秘密、安全漏洞或供应链风险；
- 无法在隔离环境稳定复现问题。

## 17. 新员工交付完成标准

一个修改只有同时具备以下内容才算完成：

- 清晰的问题单和验收标准；
- 最小且可审查的代码差异；
- 相关模块或调用链文档；
- 静态校验通过；
- 隔离环境功能测试通过；
- 数据库和接口兼容性已确认；
- 安装或升级测试通过；
- 无敏感数据泄露；
- 有回滚方案；
- PR 已审查；
- 发布物、哈希、签名和测试报告已归档。
